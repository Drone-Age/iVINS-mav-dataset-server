# iVINS Dataset Server — Process

- Версія Process: **1.0.0**
- Статус: **чинний**
- Дата набуття чинності: **2026-08-02**
- Власник: **Drone-Age**
- Область: Backend `>=3.3.0 <4.0.0`, Frontend `>=3.3.0 <4.0.0`, Distribution `>=1.0.0 <2.0.0`

Цей документ є нормативним. Він визначає політики верхнього рівня та регламенти роботи з iVINS Dataset Server. У разі суперечності між робочою інструкцією і цим документом застосовується цей документ.

## 1. Принципи

1. Безпека і цілісність даних мають пріоритет над швидкістю випуску.
2. Доступ надається за принципами мінімальних привілеїв і необхідності знати.
3. Кожна матеріальна зміна має бути простежуваною: запит, рішення, код, перевірка, реліз і результат розгортання.
4. Backend, Frontend, Process і Distribution версіонуються незалежно за SemVer.
5. `versions.json` є єдиним джерелом істини щодо версій і сумісності.
6. Автоматизація може виконувати схвалені дії, але не може самостійно розширювати права, знижувати обов'язкові перевірки або приховувати помилки.
7. Зміни мають бути оборотними; перед ризиковим розгортанням потрібні резервна копія та перевірений шлях відкату.

## 2. Ролі та дозволи

### Власник

- затверджує Process, винятки, ризики та несумісні зміни;
- призначає Maintainer, Reviewer і Operator;
- приймає рішення про публічне розкриття інцидентів.

### Maintainer

- реалізує схвалені запити на зміни;
- оновлює версії, маніфест сумісності, changelog і документацію;
- не схвалює власну високоризикову зміну одноосібно.

### Reviewer

- перевіряє код, безпеку, сумісність, тести та релізні докази;
- може зупинити випуск за невиконаної обов'язкової умови.

### Operator

- створює резервні копії, розгортає схвалені образи, перевіряє стан і виконує відкат;
- не змінює код або нормативні правила без запиту на зміну.

### Адміністратор застосунку

- керує API-ключами, Datasets, mirrors, artifacts і BAG-файлами через контрольований інтерфейс;
- не має права обходити серверну авторизацію або змінювати базу довільним SQL у штатному процесі.

Одна людина може виконувати кілька ролей у малому проєкті, але рішення, перевірка і виконання мають бути явно зафіксовані.

## 3. Заборони

Заборонено:

- створювати API-ключі у браузері або на клієнті;
- зберігати відкриті API-ключі в базі, Git, журналах, URL, cookies чи Web storage;
- розкривати секрети в issue, changelog, релізних нотатках або тестових артефактах;
- видаляти чи перезаписувати BAG-файли без явного схвалення і перевіреної резервної копії;
- розгортати несумісні версії або образ, який не пройшов обов'язкові тести;
- знімати контроль доступу, security headers, rate limits чи перевірку цілісності без схваленого винятку;
- змінювати опублікований Git tag або нормативний Process заднім числом.

## 4. Стандарти

- API-ключі генеруються виключно Backend/CLI криптографічно стійким генератором і показуються один раз.
- HTTP є свідомим обмеженням розгортання. Ключі не передаються через недовірену мережу; для зовнішнього доступу застосовується TLS-термінація, VPN або еквівалентний захищений канал.
- Автономний Distribution-пакет не містить API-ключів, бази або BAG-файлів,
  має SHA-256 inventory і розгортається без Git та мережевого завантаження.
- Кожен installer format зобов'язаний застосовувати однакові серверні межі безпеки.
- Усі локальні `.bag`/`.zip` файли зберігаються у визначеному єдиному каталозі; шлях і SHA-256 перевіряє Backend.
- Вхідні дані валідовуються сервером. Frontend не є межею безпеки.
- Залежності фіксуються, образ працює без root із мінімальними capabilities, read-only filesystem і визначеними ресурсними межами.
- Час, commit SHA, версії компонентів і результати перевірок фіксуються у релізних доказах.

## 5. Обробка запитів

1. Зареєструвати мету, ініціатора, очікуваний результат і критерії приймання.
2. Класифікувати запит: інформаційний, дефект, інцидент, зміна або реліз.
3. Визначити пріоритет, компоненти, ризик, власника та необхідні дозволи.
4. Надати підтвердження прийняття або обґрунтовану відмову.
5. Пов'язати реалізацію, тести та результат із первинним запитом.

Критичні інциденти обробляються негайно за розділом 9, не очікуючи звичайної черги.

## 6. Запити на зміни

Кожен change request містить:

- проблему, межі, поза межами і критерії приймання;
- компоненти та запропоновані SemVer-зміни, включно з Distribution;
- вплив на дані, безпеку, API, UI і сумісність;
- план реалізації, тестування, розгортання й відкату;
- необхідні схвалення та релізні докази.

High-risk зміни включають авторизацію, секрети, видалення даних, міграції, публічну мережеву доступність і несумісні контракти. Вони потребують окремого Reviewer або явного схвалення Власника.

## 7. Випуск релізів

1. Переконатися, що change request схвалений і критерії приймання виконані.
2. Визначити незалежні версії Backend, Frontend, Process і Distribution.
3. Оновити `versions.json`, компонентні changelog і відповідну документацію.
4. Запустити обов'язкові перевірки з розділу 8.
5. Зафіксувати commit SHA; робоче дерево має бути чистим.
6. Створити резервну копію даних перед зміною Backend/схеми/сховища.
7. Створити незмінні component tags, GitHub releases і автономні Distribution assets.
8. Розгорнути точний Backend image tag, вказаний у маніфесті.
9. Перевірити package checksums, `/health`, `/versions`, публічний каталог, авторизацію, адміністрування і перезапуск.
10. Записати результат; у разі помилки виконати відкат і відкрити інцидент.

## 8. Тестування

Обов'язкові release gates:

- усі unit/integration/security тести успішні;
- Docker Compose конфігурація валідна;
- production image успішно будується і запускається;
- `/health` і `/versions` відповідають маніфесту;
- гостю заборонені локальні файли, user/admin права перевірені;
- ключі не потрапляють у сховище клієнта, URL, журнал або базу у відкритому вигляді;
- Distribution bundle встановлюється на чистий target без Git і без pull/build;
- package manifest відповідає канонічним версіям і типу installer format;
- ZIP sidecar та внутрішній `SHA256SUMS` успішно перевіряються;
- перевірено цілісність і єдиний каталог BAG;
- немає незакритих Critical/High вразливостей або існує схвалений документований виняток;
- виконано smoke test після розгортання і тест restart policy.

## 9. Обробка інцидентів

1. Виявити, зареєструвати час, симптоми, вплив і джерело повідомлення.
2. Класифікувати: Critical, High, Medium або Low.
3. Стримати вплив: відкликати скомпрометовані ключі, обмежити доступ, ізолювати сервіс або зупинити небезпечну операцію.
4. Зберегти докази без розкриття секретів і без пошкодження первинних даних.
5. Усунути першопричину через emergency change request.
6. Відновити з перевіреної версії/копії та підтвердити цілісність.
7. Повідомити зацікавлених осіб відповідно до впливу.
8. Провести post-incident review: причина, хронологія, що спрацювало, дії, власники і строки.

Critical: активний витік ключів, віддалене виконання коду, масове знищення/підміна даних або повна публічна компрометація. Вимагає негайного стримування і повідомлення Власника.

## 10. Винятки

Виняток має містити правило, причину, ризик, компенсувальні заходи, власника, строк завершення і схвалення Власника. Безстрокові або незафіксовані винятки неприпустимі.

## 11. Докази та аудит

Зберігаються: change request, review, результати тестів, версійний маніфест, commit SHA, tags/releases, backup reference, deployment/smoke result, incident report і винятки. Секретні значення до доказів не включаються.

## 12. Версіонування Process

Process версіонується незалежно:

- MAJOR — несумісна зміна принципів, ролей або обов'язкових процедур;
- MINOR — нова сумісна політика, заборона, стандарт або регламент;
- PATCH — уточнення/виправлення без зміни обов'язків і дозволів.

Кожна зміна Process створює новий незмінний `process-vX.Y.Z` tag, запис у `CHANGELOG.process.md` та оновлення сумісності у `versions.json`.
